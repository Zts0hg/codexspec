### P-2026-0812-2114vj-1: Changing a chain command's auto_next successor requires regenerating derived forms during the feature

- claim: When you change a pipeline chain command's `## Auto-Next Chain Advance` successor (or insert a new chain stage), update `_AUTO_NEXT_SUCCESSOR` AND regenerate the derived install artifacts during the feature, not at release.
- type: pitfall
- scope/when: editing a chain command's auto_next successor, or inserting/removing an SDD pipeline stage, in the codexspec repo
- root-cause: `test_auto_next_section_synced_across_distribution_forms` reads the **derived** `.claude/commands/codexspec/<cmd>.md` and `.agents/skills/codexspec-<cmd>/SKILL.md` (not the template) and asserts each names its successor. Those derived files are refreshed only by `init`, so editing the template alone leaves them stale and the test red mid-feature.
- workaround: (1) update the `_AUTO_NEXT_SUCCESSOR` map in `tests/test_sdd_workflow_templates.py`, and (2) run `uv run codexspec init . --force --ai both` **during the feature** to regenerate the derived command + skill forms. Regenerating via `init` is the legitimate self-bootstrap sync, not a hand-edit.
- lesson: when a test asserts against **derived** artifacts, editing only the source leaves them stale — regenerate the derived forms in the same change; "sync derived at release" is only a catch-all.
- evidence.facts: full suite failed with `test_auto_next_section_synced_across_distribution_forms[generate-spec]` → "generate-spec template missing successor spec-to-plan" and `test_chain_commands_have_auto_next_advance[generate-spec]` after generate-spec's auto_next was retargeted to spec-to-design; the sync test reads `.claude/commands/codexspec/` and `.agents/skills/` copies. Both went green only after updating `_AUTO_NEXT_SUCCESSOR` and running `codexspec init --force --ai both` to regenerate the 9 derived command + 9 skill forms.
