# Design Document: reverse-spec

**Feature Branch**: `2026-0818-2053p5-reverse-spec`
**Created**: 2026-08-20
**Status**: Draft
**Input**: `requirements.md` (32 confirmed entries) and `spec.md` (REQ-001..021, NFR-001..006)

## Context

`reverse-spec` gives CodexSpec a brownfield entry point and an anti-drift check.
It runs in three mutually exclusive modes, selected before any output is written:

- **Overview** — no `[path]`. Architectural survey → a thin `design.md` + `slices.md`.
- **Generate** — `[path]` given, no confirmed baseline for that slice → drafted
  `spec.md` + `design.md` + a thin `requirements.md` stub, all `inferred/open`.
- **Reconcile** — `[path]` given, confirmed baseline present → `reconcile.md`
  listing drift; nothing is modified.

The design is deliberately small. `reverse-spec` is a **discipline expressed as a
command template**, matching the shape already used by `onboard`, `debug`, and
`distill`: the behavior lives in prose the agent follows, and the only Python
change is command registration. No new runtime module, no new dependency, and no
new storage mechanism is introduced.

## Architecture & Components

### C1 — Command template `templates/commands/reverse-spec.md`

The single behavioral deliverable. Frontmatter carries `description`,
`argument-hint: "[path]"`, and an `allowed-tools` list restricted to read plus
workspace-write capabilities (modeled on `onboard.md`, whose frontmatter is
`Read, Grep, Glob, Bash(git:*), Bash(ls/cat/find:*), Edit, Write`). Body sections
realize C2–C9. The derived forms under `.claude/commands/codexspec/` and
`.agents/skills/codexspec-reverse-spec/` are regenerated by `codexspec init` and
never hand-edited.

**Covers**: REQ-001, NFR-001, NFR-002

### C2 — Mode resolver

Runs first and produces exactly one mode. Order of evaluation:

1. No `[path]`, **or a path that resolves to the repository root** → **overview**.
   Baseline lookup is not performed at all, so a confirmed overview workspace can
   never divert a bare run into reconcile. An existing `<id>-overview` workspace is
   continued rather than duplicated. `reverse-spec .` is the bare run (Decision 8):
   the repository root is not a slice, which is what makes NFR-005's unconditional
   "no output aggregates the whole repository into a single detailed specification"
   true for every input rather than only for the bare form.
2. Argument is a diff or pull-request range → report the path-only contract and
   stop. Evaluated **before** path existence, so such an argument is never
   misreported as a merely invalid path.
3. `[path]` does not exist → report and stop; create no workspace.
4. `[path]` given → **normalize it** (repo-relative, `.`/`..`/absolute resolved,
   trailing slash dropped), then search `.codexspec/specs/*/` for a workspace whose
   recorded slice (C3) matches. Normalization is applied on both the write and the
   read side, so one directory spelled four ways is one slice (Decision 8). A
   workspace containing `slices.md` is an overview workspace and is skipped —
   identified by that positive marker, not by a missing `spec.md`. Both markers are
   written at workspace creation (Decision 7), so an interrupted run of either mode
   is still found by the lookup and still classified as the mode that created it.
5. Matches are sorted into **exact** (normalized slice equal) and **covering**
   (recorded slice is a proper ancestor). Only an exact match selects a mode on its
   own; a covering match never does (Decision 8).
6. Zero matches of either kind → **generate**, after checking the slice contains
   analyzable code; if it does not, report and stop without creating anything. That
   check is generate-only: in reconcile mode an emptied slice is the maximal
   `unimplemented-spec` case and must be reported as drift. A workspace recording a
   slice *inside* the given one is disclosed as an overlap but does not block.
7. Multiple exact matches → ask the user to choose; never pick the newest silently.
8. No exact match but one or more covering matches → report each and ask whether to
   use that wider workspace at its own boundary or create one for the narrower path;
   never pick silently and never quietly nest (Decision 8).
9. One exact match, artifacts `Status: confirmed` → **reconcile**.
10. One exact match, artifacts still `Status: open` → do not reconcile, but **resume
    generate** into that existing workspace rather than refusing outright. This is
    what makes REQ-016/NFR-004 resumability reachable: an interrupted generate
    leaves an open workspace, and refusing to write would strand it permanently
    while pushing the user to confirm a half-finished draft as a baseline. Never
    create a second workspace for a slice that already has one. Resume **completes
    only what is missing** (Decision 7): it appends the parts never written and
    leaves every part already present untouched, so a complete-but-unconfirmed
    draft causes no write at all and the behavior degenerates exactly to
    `spec.md` User Story 3.

**Covers**: REQ-002, REQ-008, REQ-015

### C3 — Slice identity and workspace binding

Generated `spec.md` and `design.md` carry a `Slice:` header field holding the
repo-relative path the artifacts describe, recorded in the normalized form C2
step 4 defines (Decision 8). This field is what C2 matches on, and it is the whole
baseline-lookup mechanism — there is no index file and no directory-name encoding,
which is why the normalization must be applied when the header is written and not
only when it is read. A workspace is the directory
`.codexspec/specs/<id>-<slice>/`, whose id reuses the project's
`{YYYY-MMDD-HHMM}{rr}` convention unchanged and whose slice segment derives from
the slice's final path segment (`overview` for a bare run). The directory is
created directly; `create-new-feature.sh` is deliberately **not** invoked, because
it unconditionally runs `git checkout -b` when git is present, which C10 forbids
(CON-007 supersedes the earlier mandate to call it).

Creating a workspace is one indivisible act (Decision 7): the directory is created
and the artifact that identifies it is written immediately — `spec.md` carrying the
`Slice:` header in generate mode, `slices.md` in overview mode — before any
scanning and before any derived content. There is therefore no window in which a
created workspace is invisible to C2's lookup, which is what would otherwise let an
interruption strand the first workspace and have the next run create a second one
for the same slice.

**Covers**: REQ-004, REQ-014, REQ-002, REQ-017

### C4 — Generate mode producer

Scans the slice (C9) and writes three artifacts into the new workspace:
`spec.md` (behavior and contracts), `design.md` (structure, scaled to the slice's
real complexity per the existing design-template rule), and a thin
`requirements.md` stub whose entries are all `open`. Every derived statement is
attributed to observed code, and no requirement intent is invented.

**Covers**: REQ-003, NFR-006

### C5 — Overview mode producer

Performs a high-signal architectural survey and writes an `<id>-overview`
workspace containing a thin architecture-level `design.md` (components,
responsibilities, relationships) and `slices.md` (per candidate slice: path,
one-line description, rough size or priority). It writes no `spec.md` and no
`reconcile.md`. `slices.md` is written as the workspace's creating act (C3,
Decision 7), so the C2 marker that keeps an overview workspace out of the baseline
lookup exists even when a survey is interrupted before the map is finished; a
re-run continues that workspace under the same completion-only resume rule.

**Covers**: REQ-015, NFR-005

### C6 — Inference marking and confirmation contract

Every generated `spec.md` / `design.md` carries a file-level
`Status: inferred/open` header, marks principal entries `[inferred]`, and states
in-file that it is not a reconciliation baseline until confirmed. Promotion is
performed by the user editing that header to `Status: confirmed` and appending a
**Confirmation Log** entry — the convention `requirements.md` already uses. This
feature adds no command, no flag, and no separate state file for confirmation.
The generate-mode closing summary states the exact confirmation action.

**Covers**: REQ-005, REQ-006

### C7 — Reconcile engine

Loads the slice's confirmed baseline (`spec.md`, plus `design.md` when present;
spec alone when the design was legitimately scaled away), re-reads the slice's
current code, and classifies each finding into exactly one of
`undocumented-behavior`, `unimplemented-spec`, or `semantic-mismatch`. It assigns
severity from the item's actual impact rather than from its kind, and proposes a
direction without applying it. `requirements.md` is read **only** to reason about
direction, never as a comparison baseline; when no confirmed intent covers an
item the direction is `needs-your-judgment`.

**Covers**: REQ-007, REQ-009, REQ-011, REQ-012, REQ-013

### C8 — `reconcile.md` writer

Writes the report into the resolved slice workspace using the structure fixed by
REQ-010 (Summary with baseline, code scope, `Status`, and counts; then one entry
per drift item with `id`, `kind`, `severity`, `location`, `evidence`,
`direction`, `status`; then Notes), and emits a short session briefing. The
report's `Status` and severities are presentation-only: the writer emits no
pass/fail verdict and no exit condition that any other command consumes.

**Covers**: REQ-010, REQ-011

### C9 — Scan discipline (referenced, not duplicated)

The template states that scanning follows the discipline defined in
`/codexspec:onboard` — high-signal-first, deep-read the structural and
configuration surface while shallow-sampling bulk business code, respect
`.gitignore` with a documented fallback when there is no git, stream output so the
run is interruptible and resumable, and never claim full coverage when sampling.
It is referenced by name rather than restated, the same way `implement-tasks`
references `/codexspec:debug`.

**Covers**: REQ-016, NFR-004

### C10 — Safety boundary

One boundary statement governs all three modes: read-only on the codebase; writes
confined to the resolved or created feature workspace; never writes
`.codexspec/profile/` (that store belongs to `onboard`); and never modifies source,
tests, git state, the constitution, or the baseline it reconciles against.

The clause on the workspace's own artifacts is stated as a rule rather than as a
closed list of exceptions, so that adding a legitimate write does not require
contradicting it (Decision 7). The rule: the command rewrites only what it wrote
during the current run, and never without notice. Whatever a workspace already held
when the run began is treated as the maintainer's — the command cannot distinguish
its own interrupted output from corrections the maintainer made to it, and
`spec.md` User Story 1 makes correcting the draft the expected flow — so a resumed
draft is appended to, never overwritten, and content that looks wrong is reported
rather than fixed. The single wholesale regeneration is this command's own
`reconcile.md` (C8), behind the notice REQ-010 requires.

This boundary is enforced by written discipline, not mechanically. The
`allowed-tools` frontmatter in C1 follows the `onboard` precedent and still grants
`Bash(git:*)`, `Edit`, and `Write`, so it permits far more than the boundary
allows; and `src/codexspec/integrations/codex.py` strips `allowed-tools` entirely
when rendering the Codex skill form, leaving no frontmatter restriction on that
channel at all. The contract tests in C1's test module are the strongest available
guard. Narrowing the tool grant below the `onboard` precedent would be a separate
decision and is not taken here.

**Covers**: REQ-017

### C11 — Registration and distribution lockstep

`src/codexspec/commands/installer.py` gains one `get_commands_metadata()` entry
for `reverse-spec` in the **enhanced** category adjacent to `onboard`, with a
short zh-CN description. Verified current counts to update in lockstep: the
docstring line `core (11) -> enhanced (8) -> git (3) -> review (1) -> utility (2)`
and `Total: 25 commands` become enhanced `9` and total `26`; the inline comment
`# Enhanced Commands (8)` becomes `(9)`; `tests/commands/test_installer.py`
asserts `len(result) == 25` and `len(enhanced_commands) == 8`, and
`tests/test_cli.py` asserts `"25" in result.stdout` — all three become 26/9/26.
A row is added to all 8 `README*.md` files. The command is **not** added to the
`commit_templates` set and needs no `templates/translations/*.json` entry.

The change set is bounded to exactly: the new template (C1), the installer entry
and the count sites above, the new template contract test, the 8 README rows, and
the derived artifacts regenerated by `codexspec init`. It touches **neither
constitution** — not `.codexspec/memory/constitution.md` (this repository's
governance) nor the `_get_default_constitution()` string shipped to user projects
— since nothing about this feature is a generic principle to hand every end user.

**Covers**: REQ-020, REQ-021, NFR-003

## Key Design Decisions

### Decision 1: Deliver as a pure agent-driven command template

- **Context**: The feature's behavior is judgment — reading code into a
  spec-shaped understanding and comparing it to prose. The repository already has
  three commands of exactly this shape (`onboard`, `debug`, `distill`), each a
  template plus one installer entry, contract-tested by asserting the template's
  written discipline.
- **Decision**: Implement `reverse-spec` the same way. The only Python change is
  the installer entry; tests are template contract tests in
  `tests/test_reverse_spec_template.py`, following `tests/test_onboard_template.py`.
- **Alternatives**: a Python analysis module producing structured drift. Rejected:
  drift detection here is semantic, not syntactic, so a code module would either
  be a thin wrapper around the same judgment or would restrict findings to what a
  parser can see — narrower than the confirmed requirement.
- **Trade-off**: behavior is verifiable only as written discipline, not as runtime
  assertions. Accepted, matching the established repository pattern.
- **Covers**: REQ-001, NFR-002

### Decision 2: Bind slice to workspace with an in-artifact `Slice:` field

- **Context**: REQ-002 must find the baseline for a slice, while REQ-014 gives
  each generate run its own timestamp-named workspace, so the directory name
  cannot carry the mapping.
- **Decision**: Record the slice path in a `Slice:` header inside the generated
  artifacts; lookup scans workspaces for a matching value.
- **Alternatives**: (a) a central index file mapping slices to workspaces —
  rejected because a shared index is a merge-conflict magnet, the same reasoning
  that made the profile store one-file-per-record (recorded as profile decision
  `D-2026-0812-14054p-2`); (b) encoding the path in the directory name — rejected
  because slice paths contain separators and would not survive the repository's
  kebab-case feature-name contract for spec directories.
- **Trade-off**: lookup reads candidate workspaces rather than consulting one
  index. Acceptable: spec directories are few and the read is cheap.
- **Covers**: REQ-002, REQ-004

### Decision 3: Evaluate the bare run before any baseline lookup

- **Context**: DEC-011 makes the bare run unconditionally a survey, while DEC-005
  makes mode depend on baseline presence. Round 1 of the spec review found these
  could collide once an overview design is confirmed.
- **Decision**: Order the resolver so absence of `[path]` short-circuits to
  overview mode before any baseline lookup runs.
- **Alternatives**: special-casing the overview workspace during lookup — rejected
  as the *sole* mechanism, because an easily-forgotten exception is weaker than
  never performing the lookup at all.
- **Amended during implementation**: both mechanisms are needed and both are
  implemented. The short-circuit covers the bare run; the lookup skip additionally
  covers an explicit `.` path, which is an existing directory and therefore does
  not short-circuit. Without the skip, `reverse-spec .` would match a confirmed
  overview workspace and reconcile against a design-only baseline — a state
  neither this design nor `spec.md` defines.
- **Covers**: REQ-002, REQ-015

### Decision 4: Reference `onboard`'s scan discipline instead of restating it

- **Context**: DEC-007 requires reusing the discipline; the repository's DRY
  precedent is `implement-tasks` referencing `/codexspec:debug` by name rather
  than duplicating its four phases.
- **Decision**: Name the discipline and point at `/codexspec:onboard`, stating two
  explicit overrides on the referenced text: (a) `onboard` streams findings into
  `.codexspec/profile/` and writes each convention as confirmed — that write
  directive does **not** carry over, since importing it would breach C10 and
  create a second writer for a store this command does not own (OUT-002); and
  (b) in `onboard` `[path]` narrows a profile scan, whereas here it *is* the slice
  boundary. Override (a) was added during implementation, after review found that
  delegating without it silently imported a forbidden write.
- **Trade-off**: a reader must follow one reference, and every behavioral
  difference must be enumerated as an override or it is imported by default.
  Accepted: it removes the possibility of the two disciplines drifting apart.
- **Covers**: REQ-016

### Decision 5: Bound semantic-mismatch judgment and declare what it declines

- **Context**: `semantic-mismatch` is the hardest of the three kinds and the one
  carrying the feature's core value. Over-reaching produces false drift that
  destroys trust in the report; under-reaching silently misses real deviation.
  REQ-013 already provides `needs-your-judgment` as the honest escape.
- **Decision**: The template requires each `semantic-mismatch` item to quote both
  sides as `evidence` (the code observation and the baseline text). An item that
  cannot be evidenced on both sides is not reported as a mismatch. Where a
  disagreement is visible but its correct resolution is not derivable from
  confirmed intent, the item is still reported with direction
  `needs-your-judgment`. Detection is never suppressed for lack of a direction.
- **Alternatives**: report low-confidence mismatches without both-side evidence —
  rejected, it converts the report into noise; or omit items lacking a derivable
  direction — rejected, it would hide real drift and defeat the confirmed goal.
- **Trade-off**: recall is bounded by what can be evidenced on both sides.
  Accepted as a refinement of REQ-013's existing anti-guessing rule; it changes no
  confirmed behavior. Requiring both-side evidence narrows nothing: REQ-010
  already makes `evidence` a mandatory field on every drift item.
- **Covers**: REQ-009, REQ-010, REQ-013

### Decision 6: The report is an artifact, not a gate

- **Context**: `reconcile.md` structurally resembles the `review-*` reports, which
  do act as gates with a status and score.
- **Decision**: Reuse the familiar report shape, but state in the template that
  `Status` and severity are prioritization aids only, that no command consumes
  them, and that the command emits no pass/fail verdict. Combined with C1 carrying
  no `Auto-Next Chain Advance` and no `Automatic Distillation` section, the
  command is fully decoupled from the pipeline.
- **Covers**: REQ-011, REQ-018

### Decision 7: A workspace declares itself at creation, and a resume completes rather than rewrites

- **Context**: Three separate review findings — a resume silently overwriting a
  hand-corrected draft, an interrupted overview run losing its `slices.md` marker,
  and a workspace being invisible to lookup between directory creation and the
  `Slice:` header — turned out to be one defect. The command inferred a workspace's
  identity and state from **content artifacts that are themselves written
  incrementally during the run**. Any artifact used as a state marker is also a work
  product being streamed, so mid-run the marker set is partial and a partial state is
  indistinguishable from a different state. Provenance is likewise unknowable: the
  command cannot tell its own interrupted output from the maintainer's corrections.
  Repairing the three symptoms separately produced two consecutive rounds in which
  the previous round's repair introduced the next round's worst finding.
- **Decision**: Two rules, applied together.
  1. **Identity is written before content.** Creating a workspace is one indivisible
     act: the directory plus its identifying artifact (`spec.md` with the `Slice:`
     header in generate mode, `slices.md` in overview mode), before any scanning.
     No interruption window exists in which a workspace is unfindable or readable as
     the other mode.
  2. **Resume completes; it never rewrites.** Content present when a run begins is
     treated as the maintainer's. A resumed draft is appended to; a discrepancy in
     existing content is reported, not corrected; a complete draft causes no write.
- **Why this is not new product intent**: rule 2 is strictly more conservative than
  the confirmed text and follows from REQ-017 ("MUST NOT automatically modify code
  or any pre-existing artifact") read together with `spec.md`'s confirmed boundary
  row for a re-run ("Continue the existing workspace"). It also removes the apparent
  tension between User Story 3 (refuse and report) and NFR-004 (resumability): when
  nothing is missing, completion-only *is* report-only.
- **Alternatives**: (a) prompt for consent before each overwrite — rejected, it
  introduces a confirmation mechanism REQ-006 deliberately avoids and still destroys
  work when the user answers hastily; (b) a dedicated workspace state file — rejected
  as a third mechanism where the artifacts already carry the two markers needed;
  (c) keep the closed exception list in C10 and add resume as a third exception —
  rejected, it is the shape that produced the contradiction.
- **Trade-off**: a resumed run cannot improve a section it already wrote, even when
  a wider scan would now write it better. Accepted: the alternative is destroying
  maintainer corrections, and the discrepancy is still surfaced in the report.
- **Covers**: REQ-002, REQ-004, REQ-008, REQ-015, REQ-016, REQ-017, NFR-004

### Decision 8: Normalize the slice path, and let only an exact match choose a mode

- **Context**: C2 step 4 said only that the lookup finds a workspace whose `Slice:`
  value "matches" the path. The write side was pinned to a repo-relative path; the
  read side defined neither normalization nor the match predicate. REQ-002 speaks of
  a workspace **covering** the slice and of several workspaces that **could cover**
  it, so the ambiguity was load-bearing in two directions, both reachable:
  - **Miss** — `src/auth/` (shell tab-completion), `./src/auth`, or an absolute path
    compared against a stored `src/auth` finds nothing, silently creating a *second*
    workspace for a slice that already has one and skipping the drift check that is
    the feature's confirmed purpose.
  - **False match** — with a confirmed workspace at `src/auth`, running
    `reverse-spec src/auth/tokens` yields exactly one covering match, so the
    multiple-match branch never fires. Reconcile would then write into that wider
    slice's workspace, overwriting a `reconcile.md` that holds the user's recorded
    adjudications, and report everything else under `src/auth` as
    `unimplemented-spec`.
- **Decision**: two parts.
  1. **Normalize on both sides.** Repo-relative, `.`/`..`/absolute resolved,
     trailing slash dropped — applied when the `Slice:` header is written and when
     it is compared. One directory spelled four ways is one slice.
  2. **Only an exact match selects a mode.** A covering (proper-ancestor) match is
     reported and the user chooses: use that wider workspace at its own boundary, or
     create one for the narrower path. A workspace nested *inside* the given slice
     is disclosed as an overlap but does not block.
- **Also settled here**: a path resolving to the **repository root** is the bare run
  and takes the architectural survey. This makes NFR-005's unconditional "no output
  aggregates the whole repository into a single detailed specification" hold for
  every input, and makes `reverse-spec .` and `reverse-spec` the same run — which is
  what a user would expect of them.
- **Provenance**: both parts were adjudicated by the user during implementation.
  Confirmed intent genuinely supported two readings in each case — REQ-002's
  "covering" wording against the harm covering-match reconciliation causes, and
  REQ-014's "a directory path" (the root is one) against NFR-005's unconditional
  sentence — so neither was an implementation choice to make unilaterally. Recorded
  in `requirements.md` as a Confirmation Log entry.
- **Alternatives**: (a) reconcile against the covering workspace — rejected by the
  user; it produces spurious `unimplemented-spec` for the rest of the wider slice and
  destroys another slice's recorded adjudications; (b) exact-equality only, nested
  path silently generates its own workspace — rejected; it makes REQ-002's "covering"
  and "could cover" wording and the multiple-match branch near-dead letters, and lets
  overlapping workspaces proliferate with no defined authority between them.
- **Trade-off**: one extra interaction in the covering case. Accepted: it is the same
  never-guess discipline REQ-002 already mandates for multiple matches and REQ-013
  mandates for drift direction.
- **Covers**: REQ-002, REQ-004, REQ-014, REQ-015, NFR-005

## Key Entities

| Entity | Where it lives | Fields |
|---|---|---|
| Artifact header | top of generated `spec.md` / `design.md` | `Slice:` (repo-relative path), `Status:` (`inferred/open` \| `confirmed`), plus the existing feature metadata |
| Confirmation Log entry | generated `spec.md` / `design.md` | date, what was reviewed, explicit user confirmation — the same shape `requirements.md` uses |
| Drift item | `reconcile.md` | `id`, `kind`, `severity`, `location` (code `path:line` + baseline reference), `evidence` (both sides), `direction`, `status` |
| Slice candidate | `slices.md` (overview mode) | path, one-line description, rough size or priority |

**Covers**: REQ-004, REQ-005, REQ-006, REQ-010, REQ-015

## Interface Contract

| Surface | Contract |
|---|---|
| `/codexspec:reverse-spec` | No argument → overview mode. |
| `/codexspec:reverse-spec <path>` | Path to a directory, module, or package (or a file set within one) → generate or reconcile per C2. |
| Unsupported input | A diff or pull-request range is not a slice source; the command reports the path-only contract. |
| Invalid path | Reported; no workspace and no artifacts are created. |
| Path with no analyzable code | Reported as nothing to reverse-derive; no workspace created. |

**Covers**: REQ-001, REQ-019

## Sequence & Data Flow

```text
invoke reverse-spec [path]
        │
        ├── no [path], or [path] = repo root ──────► OVERVIEW
        │                                             survey → <id>-overview/
        │                                             design.md (thin) + slices.md
        │                                             (never reconciles)
        │
        └── [path] given (normalized: repo-relative,
                          no ./ ../ , no trailing slash)
                └── find workspace whose Slice: matches
                        │   exact = equal · covering = proper ancestor
                        │
                        ├── none ──────────────────► GENERATE
                        │                            scan → new workspace:
                        │                            spec.md + design.md + requirements stub
                        │                            (all Status: inferred/open)
                        │                                     │
                        │                            user confirms (Status → confirmed
                        │                            + Confirmation Log)
                        │                                     ▼
                        ├── one, confirmed ────────► RECONCILE
                        │                            code ↔ baseline(spec[, design])
                        │                            → reconcile.md + briefing
                        │                            (reads requirements only to
                        │                             reason about direction)
                        │
                        ├── one, still open ───────► RESUME GENERATE
                        │                            report unconfirmed baseline;
                        │                            append only what is missing,
                        │                            never rewrite what is present
                        │                            (complete draft → write nothing)
                        │
                        └── several ───────────────► ASK the user to choose
```

**Covers**: REQ-002, REQ-003, REQ-007, REQ-008, REQ-010, REQ-015

## Risks & Trade-offs

| Risk | Mitigation in this design | Residual |
|---|---|---|
| Semantic-mismatch detection is shallow or noisy — the feature's core value | Decision 5: both-side evidence required to report a mismatch; `needs-your-judgment` when direction is underivable; detection never suppressed for lack of direction | Recall is bounded by what can be evidenced on both sides; genuinely subtle deviations may go unreported |
| Users never confirm, so reconcile never activates and the anti-drift value never lands | C6: the generate-mode summary states the exact confirmation action; C2 reports the unconfirmed condition explicitly instead of failing silently | Confirmation remains a manual step by confirmed design (DEC-012); this design does not add an enforcement mechanism |
| Baseline lookup misses or double-matches a slice | Decision 2 gives an explicit `Slice:` field; C2 asks the user on multiple matches rather than guessing | A hand-moved or hand-renamed slice path requires the user to update the field |
| A large repository makes the scan expensive | C9's referenced discipline is high-signal-first, streaming, and resumable | A very large repository still yields a sampled, not exhaustive, view — reported as such |
