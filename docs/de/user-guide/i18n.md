# Internationalisierung

<a id="supported-languages"></a>

Die Konfiguration liegt in `.codexspec/config.yml`. Vorlagen bleiben auf Englisch;
Agenten verfassen Dialogtexte und erzeugte Artefakte in den konfigurierten
Sprachen. Die 13 Standard-Sprachcodes sind `en`, `zh-CN`, `zh-TW`, `ja`, `ko`,
`es`, `fr`, `de`, `pt`, `ru`, `it`, `ar` und `hi`.
Für Portugiesisch verwendet die CLI `pt`; lokalisierte Dokumentation und
Übersetzungskataloge verwenden `pt-BR`.

<a id="language-dimensions"></a>

## Sprachdimensionen

| Dimension | Konfigurationsschlüssel | Bei der Initialisierung | Später festlegen | Steuert |
|-----------|------------|-------------------|-----------|----------|
| Ausgabe/Basis | `language.output` | `--lang` | `config --set-lang` | Ersatzwert für die anderen Sprachdimensionen |
| Interaktion | `language.interaction` | `--interaction-lang` | `config --set-interaction-lang` | Gespräche und CLI-Ausgabe |
| Dokument | `language.document` | `--document-lang` | `config --set-document-lang` | Anforderungen, Spezifikationen, Entwürfe, Pläne und Aufgaben |
| Commit | `language.commit` | `--commit-lang` | `config --set-commit-lang` | Commit-Nachrichten und Texte aus den Git-Workflows |

Ist für eine Dimension keine spezifische Sprache gesetzt, wird unabhängig von
den anderen Dimensionen `language.output` verwendet. Ist auch dieser Wert nicht
gesetzt, gilt `en`. `language.templates` bleibt `en`.

```bash
codexspec init my-project --ai both \
  --interaction-lang zh-CN --document-lang en --commit-lang en

codexspec config
codexspec config --set-document-lang en
codexspec config --list-langs
```

Bei der erstmaligen Initialisierung mit TTY wird die Basissprache abgefragt,
sofern Sie weder `--lang` noch alle drei spezifischen Sprachoptionen angeben.
`--force` bestätigt andere Initialisierungsrückfragen automatisch, unterdrückt
aber diese Sprachauswahl nicht. Ohne TTY wird standardmäßig Englisch verwendet.
Bei erneuter Initialisierung bleiben Sprachschlüssel erhalten, die Sie nicht
explizit setzen.

## Übersetzte Dokumentation

Die Website und die READMEs im Stammverzeichnis werden in acht Sprachen gepflegt. Die Spracheinstellungen zur Laufzeit steuern die Ausgabe des Agenten; sie übersetzen die Repository-Dokumentation nicht automatisch. Die englischen Seiten unter `docs/en/` sind die Übersetzungsquelle. Englisch wird im Stammverzeichnis der Website veröffentlicht, die anderen Versionen unter ihren Sprachpfaden.

[English](https://zts0hg.github.io/codexspec/) · [中文](https://zts0hg.github.io/codexspec/zh/) · [日本語](https://zts0hg.github.io/codexspec/ja/) · [한국어](https://zts0hg.github.io/codexspec/ko/) · [Español](https://zts0hg.github.io/codexspec/es/) · [Français](https://zts0hg.github.io/codexspec/fr/) · [Deutsch](https://zts0hg.github.io/codexspec/de/) · [Português](https://zts0hg.github.io/codexspec/pt-BR/)

## Übersetzungen pflegen

Verwenden Sie in einem der beiden Assistenten die Repository-eigenen Einstiege für Übersetzung und semantische Prüfung. Diese Wartungswerkzeuge gehören nicht zu den öffentlichen Befehlen, die `codexspec init` installiert. Die gemeinsamen Regeln stehen in `internal/references/doc-translation.md`, die Terminologie in `docs/i18n/glossary.yml`.

```text
$codexspec:translate-docs --source docs/en/getting-started/installation.md --lang all
$codexspec:check-i18n-semantics --source docs/en/getting-started/installation.md --lang all --strict

/codexspec:translate-docs --source docs/en/getting-started/installation.md --lang all
/codexspec:check-i18n-semantics --source docs/en/getting-started/installation.md --lang all --strict
```

Wählen Sie die geänderten englischen Seiten aus, lesen Sie die vollständige Quelle und erhalten Sie alle Bedingungen, Standardwerte, Ausschlüsse, Beispiele und technischen Tokens. Schreiben Sie natürlich klingende technische Dokumentation in der Zielsprache; die englische Satzstruktur muss nicht erhalten bleiben. Prüfen Sie inhaltliche Treue und sprachliche Natürlichkeit getrennt und gleichen Sie übersetzte Überschriftenlinks mit ihren Zielseiten ab.

Das Inventar erfasst die genauen Quell-/Zieldateipaare und die Hashes der Quellen. Mechanische Prüfungen erkennen Unterschiede bei Struktur, Codebeispielen, Tokens und Links, belegen aber keine semantische Gleichwertigkeit. Prüfen Sie jede ausgewählte Sprache und beheben Sie Auslassungen oder unnatürliche Formulierungen, bevor Sie die Übersetzung akzeptieren. Ein Probelauf zeigt nur die Auswahl an.

## Build und Diagramme prüfen

Die Dokumentations-CI baut die Website mit strenger MkDocs-Validierung. Übersetzung und semantische Prüfung bleiben eigenständige Wartungsaufgaben; ein erfolgreicher Build allein belegt keine Übersetzungsqualität. Prüfen Sie die betroffenen Seiten, die Sprachnavigation, schmale Ansichten und beide Farbschemata in der Vorschau.

```bash
uv sync --extra dev --extra docs
uv run python -B -m internal.doc_translation inventory --lang all
uv run python -B -m internal.doc_translation verify --lang all
uv run mkdocs build --strict
uv run mkdocs serve
```

Die Website nutzt über `hooks/workflow_assets.py` dieselben Workflow-PNGs aus `assets/workflow/` wie die READMEs. Sie hält keinen zweiten Satz von Quellbildern in den Dokumentationsverzeichnissen vor. Die themenspezifischen Bildlinks folgen der Hell-/Dunkel-Umschaltung der Website. Aktualisieren Sie Diagrammquelle, Kataloge, Layout und sämtliche erzeugten Dateien nach dem gemeinsamen Wartungshandbuch.
