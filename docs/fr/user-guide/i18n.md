# Internationalisation

<a id="supported-languages"></a>

La configuration est enregistrée dans `.codexspec/config.yml`. Les modèles
restent en anglais ; l'agent rédige les échanges et les artefacts générés dans
les langues configurées. Les 13 codes de langue standard sont `en`, `zh-CN`,
`zh-TW`, `ja`, `ko`, `es`, `fr`, `de`, `pt`, `ru`, `it`, `ar` et `hi`.
Pour le portugais, la CLI utilise `pt` ; la documentation localisée et les
catalogues de traduction utilisent `pt-BR`.

<a id="language-dimensions"></a>

## Langues des échanges, des documents et des commits

| Dimension | Clé de configuration | À l'initialisation | Modifier ensuite | Ce qu'elle contrôle |
|-----------|------------|-------------------|-----------|----------|
| Sortie/base | `language.output` | `--lang` | `config --set-lang` | Langue de repli pour les autres dimensions |
| Échanges | `language.interaction` | `--interaction-lang` | `config --set-interaction-lang` | Conversation et sortie de la CLI |
| Documents | `language.document` | `--document-lang` | `config --set-document-lang` | Exigences, spécifications, documents de conception, plans et tâches |
| Commits | `language.commit` | `--commit-lang` | `config --set-commit-lang` | Messages de commit et textes générés dans les flux de travail Git |

Si la langue d'une dimension n'est pas définie, `language.output` est utilisée,
puis `en` à défaut. Cette règle s'applique indépendamment à chaque dimension.
`language.templates` reste à `en`.

```bash
codexspec init my-project --ai both \
  --interaction-lang zh-CN --document-lang en --commit-lang en

codexspec config
codexspec config --set-document-lang en
codexspec config --list-langs
```

Lors de la première initialisation depuis un terminal TTY, la langue de base
vous est demandée, sauf si vous fournissez `--lang` ou les trois options de
langue spécifiques. `--force` confirme automatiquement les autres demandes
d'initialisation, mais ne supprime pas cette sélection. Sans TTY, l'anglais est
utilisé par défaut. Une nouvelle initialisation conserve les clés de langue
que vous n'avez pas explicitement définies.

## Documentation traduite

Le site et les README à la racine sont maintenus en huit langues. Les réglages linguistiques à l’exécution contrôlent la sortie de l’agent ; ils ne traduisent pas automatiquement la documentation du dépôt. Les pages anglaises de `docs/en/` servent de source. L’anglais est publié à la racine du site, les autres versions sous leur chemin de langue.

[English](https://zts0hg.github.io/codexspec/) · [中文](https://zts0hg.github.io/codexspec/zh/) · [日本語](https://zts0hg.github.io/codexspec/ja/) · [한국어](https://zts0hg.github.io/codexspec/ko/) · [Español](https://zts0hg.github.io/codexspec/es/) · [Français](https://zts0hg.github.io/codexspec/fr/) · [Deutsch](https://zts0hg.github.io/codexspec/de/) · [Português](https://zts0hg.github.io/codexspec/pt-BR/)

## Maintenance des traductions

Utilisez les entrées de traduction et de revue sémantique propres au dépôt dans l’un ou l’autre assistant. Ce sont des outils de maintenance, pas des commandes publiques installées par `codexspec init`. Les règles communes se trouvent dans `internal/references/doc-translation.md` et la terminologie dans `docs/i18n/glossary.yml`.

```text
$codexspec:translate-docs --source docs/en/getting-started/installation.md --lang all
$codexspec:check-i18n-semantics --source docs/en/getting-started/installation.md --lang all --strict

/codexspec:translate-docs --source docs/en/getting-started/installation.md --lang all
/codexspec:check-i18n-semantics --source docs/en/getting-started/installation.md --lang all --strict
```

Sélectionnez les pages anglaises modifiées, lisez toute la source et conservez chaque condition, valeur par défaut, exclusion, exemple et jeton technique. Rédigez une documentation technique naturelle dans la langue cible ; il n’est pas nécessaire de conserver la structure des phrases anglaises. Évaluez séparément la fidélité et la fluidité, puis vérifiez les liens vers les titres traduits dans leurs pages de destination.

L’inventaire enregistre les paires exactes de fichiers source et cible ainsi que les empreintes des sources. Les contrôles mécaniques détectent les différences de structure, d’exemples de code, de jetons et de liens ; ils ne prouvent pas l’équivalence sémantique. Examinez chaque langue sélectionnée et corrigez les omissions ou formulations peu naturelles avant d’accepter la traduction. Une simulation ne fait qu’afficher la sélection.

## Vérification du build et des diagrammes

La CI de documentation effectue le build avec la validation stricte de MkDocs. La traduction et la revue sémantique restent des travaux de maintenance explicites ; un build réussi ne suffit pas à garantir la qualité des traductions. Prévisualisez les pages concernées, la navigation entre langues, les mises en page étroites et les deux thèmes.

```bash
uv sync --extra dev --extra docs
uv run python -B -m internal.doc_translation inventory --lang all
uv run python -B -m internal.doc_translation verify --lang all
uv run mkdocs build --strict
uv run mkdocs serve
```

Le site réutilise les PNG du workflow du README dans `assets/workflow/` via `hooks/workflow_assets.py` ; il ne conserve pas un second jeu d’images sources dans les répertoires de documentation. Les liens d’images propres à chaque thème suivent le sélecteur clair/sombre du site. Mettez à jour la source du diagramme, les catalogues, la mise en page et tous les fichiers générés en suivant le manuel de maintenance commun.
